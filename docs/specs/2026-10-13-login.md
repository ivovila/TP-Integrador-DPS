# Spec · Login y logout

Fecha: 2026-10-13 · Rama: `entrega-2-spec1` · Continúa [Roles en el frontend](2026-10-13-frontend-roles.md).

## 1. Objetivo

Hoy la API cree a quien diga ser cada request: `ActingPersonResolver` arma la `Person` con los headers
`X-Person-Id` y `X-Person-Name`, y los roles solo ocultan botones en la interfaz. Esta fase agrega autenticación
con Spring Security y convierte los roles en un control de acceso real del backend.

La autenticación no es un recurso: cualquier path acepta credenciales, como pide REST sin estado. La contraseña
viaja una sola vez; a partir de ahí el cliente usa un token firmado que expira y que el logout revoca en el
servidor.

### Criterios de aceptación

1. Cualquier request puede autenticarse con `Authorization: Basic base64(personId:password)`. Si las credenciales
   son válidas, la respuesta (sea cual sea su estado) trae un JWT en `Authorization: Bearer <jwt>` y su
   vencimiento en `Token-Expires`.
2. Un request con `Authorization: Bearer <jwt>` válido se atiende como esa persona.
3. Sin credenciales, con credenciales incorrectas o con un token vencido, mal firmado o revocado, la API responde
   **401** problem+json. Ningún path de `/api/v1` responde sin autenticación.
4. `DELETE /api/v1/tokens/current` revoca el token con el que se hace el request y responde **204**. Desde ese
   momento ese token recibe 401; otros tokens de la misma persona siguen valiendo.
5. Cada escritura exige el rol de §3; con otro rol la API responde **403** problem+json. Toda lectura (GET) la
   puede hacer cualquier persona autenticada.
6. La persona que actúa sale del token: los headers `X-Person-*` dejan de existir. Los controladores siguen
   recibiendo `@ActingPerson Person` sin cambios.
7. El frontend tiene una pantalla de login y un botón de logout; el selector "Acting as" desaparece.
8. `certiflow-domain` y `certiflow-application` no cambian.

### Fuera de alcance

- Alta, baja o edición de usuarios y cambio de contraseña: los usuarios se cargan por datos.
- Refresh tokens: al vencer el token (1 hora) se vuelve a ingresar.
- "Cerrar todas las sesiones" de una persona.
- Restringir registros por persona (que el responsable vea solo sus activos) o validar que quien planifica una
  acción sea el responsable de ese hallazgo: siguen siendo reglas del dominio existentes o deuda.
- Ocultar en los links HAL las acciones que el rol no puede hacer: la API sigue ofreciendo lo que el estado
  permite y la interfaz filtra por rol (D24).

## 2. Flujo

| Situación | Request | Respuesta |
|---|---|---|
| Ingresar, por cualquier path | `Authorization: Basic …` | la respuesta normal del endpoint + `Authorization: Bearer <jwt>` + `Token-Expires: <instante ISO-8601>` |
| Uso normal | `Authorization: Bearer <jwt>` | la respuesta normal |
| Sin credenciales, credenciales incorrectas, token vencido o revocado | — | 401 problem+json |
| Escritura con un rol que no corresponde | Bearer | 403 problem+json |
| Logout | `DELETE /api/v1/tokens/current` + Bearer | 204 |
| Logout con Basic en lugar de Bearer | `DELETE /api/v1/tokens/current` + Basic | 400 problem+json: no hay token que revocar |

- **Contenido del JWT:** `sub` = id de la persona, `name`, `role`, `jti` (UUID), `iat`, `exp`. Firmado con
  HMAC-SHA256. El frontend lee persona y rol del token: no hace falta un endpoint "quién soy".
- **Diálogo del navegador:** una respuesta 401 con `WWW-Authenticate: Basic` hace que el navegador abra su propio
  diálogo de login. Spring Security no manda ese header cuando el request trae
  `X-Requested-With: XMLHttpRequest`; el frontend lo envía siempre. Los demás clientes (curl, tests) reciben el
  desafío `Basic` normal.
- **Por qué el logout sí tiene path:** ingresar solo prueba identidad y no cambia nada en el servidor; revocar
  sí cambia algo (marca un token como muerto), y en REST eso se hace sobre un recurso. `tokens/current` nombra
  la credencial con la que se está hablando, como `/users/me`: nadie puede revocar un token ajeno porque nunca
  nombra otro. Es el mismo esquema que el endpoint de revocación de OAuth 2.0 (RFC 7009).

## 3. Roles en el backend

Los seis roles de [Roles en el frontend](2026-10-13-frontend-roles.md) §2, ahora aplicados por la API.

| Rol (`role` en el token) | Escrituras permitidas |
|---|---|
| `ADMINISTRATOR` | `POST /assets` · `POST /schemas` · `POST /schemas/{type}/versions` |
| `INSPECTION_COORDINATOR` | `POST /inspections` |
| `INSPECTOR` | `PUT /inspections/{id}/responses/{code}/answer` · `POST …/evidence` · `POST …/observations` · `POST /inspections/{id}/closure` · `POST /inspections/{id}/rectifications` |
| `ASSET_RESPONSIBLE` | `POST /findings/{id}/corrective-actions` |
| `VERIFIER` | `POST /findings/{id}/corrective-actions/{actionId}/verifications` |
| `CERTIFICATION_OFFICER` | `POST /certificates` · `POST /certificates/{n}/suspensions` · `POST /certificates/{n}/renewals` · `POST /certificates/{n}/global-renewals` · `POST /assets/{code}/global-certificates` |

`DELETE /tokens/current` lo puede hacer cualquier persona autenticada. Cada método de escritura de los
controladores lleva `@PreAuthorize("hasRole('…')")`: la regla queda al lado del endpoint que protege. Se descartó
listar patrones de URL en la configuración de seguridad porque separa la regla del endpoint y un cambio de path la
rompe sin aviso.

## 4. Diseño

### Dónde vive

Usuarios y contraseñas no son parte del dominio de CertiFlow: quién actúa ya es una `Person` del dominio, y cómo
lo prueba es un detalle técnico. Por eso no cambian `certiflow-domain` ni `certiflow-application`.

- **`certiflow-infrastructure`, paquete `infrastructure.security`:**
  - Tablas agregadas a `V1__init.sql` (no hay datos que conservar; se recrean las bases locales):
    `user_account (person_id PK, name, role, password_hash)` y `revoked_token (jti PK, expires_at)`.
  - Entidades JPA y repositorios Spring Data para ambas tablas.
- **`certiflow-web`, paquete `web.security`:**
  - `spring-boot-starter-security` y `spring-boot-starter-oauth2-resource-server` (validación JWT de Spring, sin
    parseo propio). `NimbusJwtEncoder`/`NimbusJwtDecoder` con la clave HMAC.
  - `SecurityProperties` con `@ConfigurationProperties("certiflow.security.jwt")`: `secret` (obligatorio, mínimo
    32 bytes; en `application.properties` se lee de `CERTIFLOW_JWT_SECRET` con un valor de desarrollo por defecto)
    y `ttl` (por defecto `PT1H`).
  - Un `UserDetailsService` sobre `user_account`, con contraseñas BCrypt (`DelegatingPasswordEncoder`).
  - `SecurityFilterChain`: sin sesión HTTP (`STATELESS`), CSRF desactivado (no hay cookies), `httpBasic()` y
    `oauth2ResourceServer().jwt()` a la vez, todo `/api/v1/**` autenticado, `@EnableMethodSecurity`.
  - Un filtro que, cuando la autenticación del request fue por Basic y salió bien, emite el JWT y agrega los
    headers de §2 antes de que se escriba la respuesta.
  - Un `OAuth2TokenValidator<Jwt>` que rechaza los `jti` presentes en `revoked_token`.
  - `TokenController`: `DELETE /api/v1/tokens/current` guarda el `jti` con su `exp` y, en la misma transacción,
    borra los revocados ya vencidos para que la tabla no crezca.
  - `ActingPersonResolver` lee `sub` y `name` del JWT autenticado (o del usuario de Basic) en lugar de los headers.
  - Los 401 y 403 salen como problem+json, igual que los demás errores (`ApiExceptionHandler`).
  - El rol del token se convierte en la autoridad `ROLE_<rol>`.

### Usuarios de ejemplo

Un `DemoUsersSeeder` activo con los perfiles `demo` y `demo-users` crea, si no existen, las seis personas de hoy
con la contraseña `certiflow`:

| Id | Nombre | Rol |
|---|---|---|
| EMP-006 | Ana Torres | ADMINISTRATOR |
| EMP-001 | Paula Rios | INSPECTION_COORDINATOR |
| EMP-002 | Ines Duarte | INSPECTOR |
| EMP-003 | Raul Mendez | ASSET_RESPONSIBLE |
| EMP-004 | Vera Soto | VERIFIER |
| EMP-005 | Carlos Vidal | CERTIFICATION_OFFICER |

No van en la migración: las credenciales de ejemplo nunca llegan a una base real. `demo` carga además los activos
y esquemas de `DemoDataSeeder`; `demo-users` solo los usuarios, para el job e2e, que carga sus datos por la API.

### Frontend

- **Pantalla de login** (ruta `/login`): id de persona y contraseña. Envía Basic en `GET /api/v1` y guarda el
  token en `sessionStorage` (recargar la página no cierra la sesión; cerrar la pestaña sí). Persona y rol salen
  del payload del token.
- **`HalClient`** manda `Authorization: Bearer …` y `X-Requested-With: XMLHttpRequest` en lugar de `X-Person-*`.
  Un 401 borra el token y lleva al login; un 403 se muestra como error, como los demás rechazos.
- **Encabezado**: se elimina `ActingPersonPicker`; se muestra la persona, su rol y un botón **Logout** que hace
  `DELETE /api/v1/tokens/current`, borra el token y vuelve al login (aunque el DELETE falle).
- Sin token, cualquier ruta lleva al login.
- `roles.ts` y la intersección "acción permitida por el sistema y por el rol" no cambian; el rol ahora viene del
  token. `roster.ts` queda solo para los selectores de persona de los formularios.
- `npm run seed` y la suite e2e ingresan con Basic como el usuario de cada paso, en lugar de mandar headers.

### CI

El job `e2e` levanta el backend con `-Dspring-boot.run.profiles=demo-users`. El job `build` no cambia.

## 7. Decisiones confirmadas (2026-10-13)

1. **Login + roles aplicados en el backend**, no solo en la interfaz.
2. **Usuarios en PostgreSQL**, en una tabla propia; las tablas se agregan a `V1__init.sql` en lugar de una
   migración nueva, porque no hay datos que conservar.
3. **JWT** como credencial después del ingreso.
4. **Ingreso por cualquier path con Basic**; no hay endpoint de login.
5. **Logout revocando en el servidor** con `DELETE /api/v1/tokens/current`.
6. **`@PreAuthorize`** en cada escritura.
